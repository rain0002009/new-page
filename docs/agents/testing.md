# 测试范围与验证边界

2026-11-25 规则确立：针对性验证改动缝隙，防止日常研发中运行无关测试或全量测试浪费时间与资源。

## 核心原则

任何新增需求、功能变更或缺陷修复，只验证受本次改动影响的最窄逻辑与功能缝隙。严禁无差别触发全量测试套件。

## 验证梯级

1. **类型检查**：`pnpm typecheck`
   - 改动涉及 TypeScript 接口、状态协议或业务代码时必须执行。
2. **快速单元测试**：`pnpm vitest run [测试文件]`
   - 验证纯逻辑、状态合并、序列化及领域计算。Vitest 纯内存运行（毫秒级），可运行针对性测试文件或全局单元测试（`pnpm vitest run`）。
3. **针对性 E2E 浏览器验收**：`pnpm exec playwright test <spec文件> -g "<匹配用例名>"`
   - Playwright 涉及打包 Chrome 扩展并在真实浏览器环境中启停，开销极高。
   - 必须使用 `-g` 过滤出与当前改动强相关的具体用例，或仅执行新建的专用 spec 测试文件。

## 范围限制

- **日常开发禁止全量 E2E**：在日常功能开发、缺陷排查、重构与 Issue 验收过程中，严禁执行无过滤的 `playwright test`、`pnpm test:e2e` 或 `pnpm test:all`。
- **全量测试触发条件**：仅在以下两种情况被明确满足时，才允许执行全量回归：
  1. 用户在对话中明确要求进行全量回归验证；
  2. 准备正式发布并提交 Chrome 应用商店审核（执行 `pnpm package:chrome` 之前）。

## Issue 与验收规范

- 在需求分析与规格产出（`/to-spec`）时，必须在 Issue 的 `Testing Decisions` 中列出**具体的针对性验证命令**（包含文件路径与 `-g` 过滤器）。
- 在实施与验收（`/implement`）时，以针对性测试全部通过作为验证完成标志（Completion Criterion），记录执行证据并交付，不再额外寻找历史无关用例执行。
