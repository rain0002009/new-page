# 自建 WebDAV 连接失败诊断

日期：2026-11-10。检查本地 `C:/workspace/webdav` 的 Worker 源码；未使用真实网盘凭据，未验证线上部署与本地源码是否完全一致。

## 已验证的响应链

使用真实 `handleWebDavRequest`、`QuarkAdapter`、`QuarkClient`，仅替换鉴权和上游 HTTP 传输，运行约两秒的隔离复现：

```text
First MKCOL: 502; directory exists: true; body: Failed to verify created directory.
Second MKCOL: 201
Probe PUT: 201; GET: 200; ETag: null
Invalid If-Match PUT: 201; upload calls: 2
```

1. 模拟上游目录列表在创建后一次读取中仍返回旧列表，真实适配器的立即校验失败并返回 502；等待路径缓存过期后重试成功。只取消列表延迟时首次 MKCOL 变为 201。这证明此实现可以产生用户报告的目录现象，尚不能证明线上那次 502 就是这个原因，需要线上脱敏响应或日志确认。
2. 即使上游下载包含强 ETag，`worker/webdav.ts` 的 GET 响应也不转发它；PUT 响应同样没有文件版本。无需列表延迟即可复现版本错误。
3. `handlePut` 不读取 `If-Match` / `If-None-Match`。错误版本仍进入 `putFile`，删除已有文件并上传，返回 201。这证明补充 ETag 响应头本身不足以实现并发保护。

连接探测失败后会删除自身的临时文件，业务数据尚未上传，因此看到空目录符合当前连接流程。

## 客户端处理

继续拒绝没有可靠版本或忽略写入条件的服务。错误明确指出 GET / PUT 缺少强 ETag，以及需要升级服务端。连接探测也检查 PUT 响应的版本，避免到首次上传业务数据后才发现写入响应缺少版本。探测失败不启用新数据源，清理临时文件，已有本地数据不删除。

浏览器回归覆盖 GET 缺失版本、PUT 缺失版本、忽略条件写入、修正服务端后再次连接。GET / PUT 两个回归先在旧构建上失败：前者提示不具体，后者已经进入工作台，未在连接阶段拒绝。

修复后 `pnpm typecheck`、`pnpm build:chrome` 通过；`pnpm test:e2e -g '缺少 ETag|认证失败与不安全|首次连接后添加收藏'` 的四条真实 Chrome 测试全部通过（18.1 秒）。本次未重复运行不受影响的其他浏览器测试。

## 服务端修复要求

- 创建目录不能把最终一致的列表立即查询当作唯一成功依据；优先使用已确认的创建结果，并处理目录可见性延迟。线上 502 还需核实具体响应。
- GET 和成功 PUT 必须返回与实际文件内容对应的强 ETag。
- `If-None-Match: *`、`If-Match` 的校验与写入必须原子化；条件不满足返回 412，不能触发删除或上传。
- 普通 Worker isolate 内的锁或 KV 中先读后写不能替代跨实例原子保护。需要选择具有可靠并发协调能力的实现，并覆盖两客户端同时创建、持有旧版本覆盖、失败上传和重试。
- 采用 Durable Object 协调时还必须处理 Quark 上游列表/下载延迟与写入失败恢复，不能只加锁或透传下载 ETag 就宣称安全。

继续完善自建服务需要服务端实现与部署；切换到具备这些能力的 WebDAV 也可保持当前客户端协议。客户端改动不代表线上服务已经修好。
